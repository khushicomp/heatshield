# Amplify blank-screen repair

> Incident and repair record. On the October 11 submission recheck, the public index
> and its slash-path JavaScript/CSS assets returned HTTP 200 with correct content
> types. The owner reports successful dashboard allocations. The failure and
> manual-upload instructions below describe the earlier incident; no redeployment
> is needed for submission documentation. GitHub build configuration remains a
> prepared option, not a verified active pipeline.

## Confirmed cause

On October 11, 2026, the public site
https://staging.d22u8i6a71q15e.amplifyapp.com/ returned HTTP 200 and an index identical
to local frontend/dist/index.html. The referenced URLs `/assets/index-9JCD9-O2.js`
and `/assets/index-QTfq0zqT.css` returned 404. The encoded-backslash JavaScript URL
`/assets%5Cindex-9JCD9-O2.js` returned 200 with JavaScript content type.

Inspection of the existing ZIP revealed **different path separators in its two
header structures**: the central directory listed `assets/index-9JCD9-O2.js`, but
the local file header contained `assets\index-9JCD9-O2.js`. CSS had the same defect.
This explains why ZIP listings looked correct while Amplify published assets under
backslash paths. Re-uploading the same ZIP repeats the defect. Changing Vite's
correct root-relative base or rewriting missing scripts to index.html is not a fix.

The replacement Python packager explicitly writes portable forward-slash paths,
checks both header structures and verifies file bytes. A regression fixture
reproduces the misleading good-listing/bad-local-header ZIP.

## Fastest repair: keep the working staging origin

From the repository root, using the existing API origin (no backend change):

```powershell
cd frontend
$env:VITE_API_BASE_URL = 'https://hdt6pym543.execute-api.ap-southeast-2.amazonaws.com'
npm ci
npm test
npm run build:deploy
cd ..
python -B scripts/package_frontend.py
```

Upload **outputs/heatshield-frontend.zip**, newly generated by this script, to the
existing Amplify app **d22u8i6a71q15e**, branch **staging**. Do not regenerate it with
Compress-Archive. Keep the same hostname so that the working API's CORS configuration
does not need to change. Upload via the normal AWS console; no credentials in chat.
Manual ZIP deployment does not execute amplify.yml.

After deployment, run:

```powershell
cd frontend
npm run verify:public -- https://staging.d22u8i6a71q15e.amplifyapp.com/
```

This fetches the deployed index and every referenced JS/CSS URL, requiring HTTP 200,
correct content types and non-HTML bodies. It deliberately fails on SPA rewrites
that return index.html for an asset. Then open the site in a fresh browser session,
confirm no console errors, run an allocation and check charts and authoritative
totals. A successful build or Amplify job alone does not establish a working site.

## Preferred ongoing deployment: GitHub

The root amplify.yml uses the official monorepo shape:

- appRoot frontend; set AMPLIFY_MONOREPO_APP_ROOT=frontend.
- Node 24, npm ci, frontend tests, production deployment build and asset checks.
- Artifact directory dist relative to frontend; include **/* without flattening.
- No backend build, Amplify backend environment, SSR or Python deployment.

The deployment build fails if the API origin is missing or a placeholder. Set
VITE_API_BASE_URL to the existing HTTPS API origin above in Amplify branch settings;
it is public configuration. Vite embeds it at build time, so rebuild after changes.

The current source/config changes must be reviewed, committed and pushed before
GitHub deployment can use them. Connect khushicomp/heatshield through the normal
GitHub/Amplify authorization UI and select the branch containing these changes.
If the existing manual app offers repository connection, preserve the staging
hostname. Otherwise keep the repaired manual app for this deadline; a new Git-based
app gets a different origin and may require a separately approved CORS change.
Do not change the working API Gateway as part of this frontend repair.

Do not add a broad /* → /index.html rewrite. This dashboard has no client-side
routes and does not need an SPA catch-all. Inspect existing rewrite rules for asset
interception. If routing is introduced later, use an extension-excluding rule from
AWS documentation, never return HTML for JS/CSS.

Sources: [AWS monorepo configuration](https://docs.aws.amazon.com/amplify/latest/userguide/monorepo-configuration.html),
[manual deployment](https://docs.aws.amazon.com/amplify/latest/userguide/manual-deploys.html),
[rewrite examples](https://docs.aws.amazon.com/amplify/latest/userguide/redirect-rewrite-examples.html).

## Verification boundary

No authenticated AWS access is available in the development session. The public
404/backslash-path diagnosis is verified through read-only HTTPS requests; updating
the hosting deployment requires the manual upload above. No Lambda or API Gateway
configuration, scientific calculations, UI behavior or dependency versions change.

Local repair verification passed 72 Python tests and 16 frontend tests. The
production deployment build passed using the same API origin already embedded in
the existing build. The replacement ZIP is 190,678 bytes; both ZIP header structures
are checked. Serving its extracted contents returned HTTP 200 for index, JS and CSS,
with exact asset bytes and correct content types. Chrome rendered the production
dashboard with its disclosures and Run allocation control, without runtime
exceptions. The API request was not tested from localhost because its browser
origin differs from the approved public origin. The existing Vite bundle-size
advisory remains. Public slash-path assets still require the corrected deployment;
the GitHub configuration is prepared but has not been committed or deployed.
